## 背景与问题

用本技能对"重庆药大麦医药科技有限公司"做关联方主动发现核查（穿透 5 层、候选上限 300 家）时，发现候选环节成功（107 家候选及 5 层股权路径已保存），但下载资料环节失败：108 家（被审计单位 + 107 家候选）实际下载成功 0 家，已生成的报告"比对 0 家、疑似关联方 0 家"，不具结论价值，需在技能修好后续跑重出。

已确认的三个问题：

1. **半截任务续跑崩溃**（已修复，提交 70b7e63）：进度文件缺失时续跑直接崩溃，现按全新开始处理。
2. **状态写入扛不住 Windows 文件占用**（已修复，提交 8a6e72f）：并发写同一状态文件时临时名互踩，现临时名带进程号、重试加至 5 次。
3. **下载失败 + 逐家取数不落盘**（待修，即本需求）：下载全失败的真实原因当时未测准；且逐家取数把所有企业攒在内存里、全部抓完才写盘，一次故障废掉整轮进度。

## 用户与使用场景

审计人员发起一次主动发现核查，任务要连续跑数小时。期间用户会正常使用电脑（切换窗口、用别的软件、在 Edge 里看别的页面），不能要求全程盯着或不许动浏览器。人工干预越少越好：能自动恢复就不暂停，能留痕继续就不问；但不得静默吞掉真实报错，不得把没拿到的资料说成"正常范围外"。

## 调研摘要与来源（2026-10-25 本机只读实测）

- opencli 通道本身正常：同步求值 0.3—0.7 秒返回（`1+1`、`location.href` 均通）。
- **页面停摆复现**：会话标签页处于后台（`document.visibilityState = hidden`）时，页面内 300 毫秒定时器等待 12 秒不触发，页面内 `fetch` 永不完成；`opencli` 对应调用直至超时，报 `OSError: opencli 调用超时`。
- **自愈路径有效**：新建标签页后立即恢复——定时器准时完成，`fetch` 拿到 HTTP 200、业务 `status_code=0 请求成功`。
- **报错外壳吞真因**：上述底层错误（调用超时 / 调用失败 / 扩展断连）在客户端统一翻成"网络错误达到重试上限"，只保留外壳、丢失具体原因，这正是当时查不到根因的原因。
- 与历史现场（情况说明第三节）对照："Edge 曾被关闭""页面被原生对话框阻塞""约 14—17 秒失败一次"分别对应快速失败路径（opencli 快速报错 + 限速等待 + 两次退避），与本次实测的挂起路径（60 秒超时）是同一类"页面不干活"的不同表现，统一表现为外壳报错。
- 结论：108 家全军覆没最可能是下载中途页面层失效（标签页被冻结、被对话框挡住、浏览器被关之一或叠加），具体是哪一种已无法从旧报错回溯；修复必须覆盖这一整类，而不是修某一个点。

## 功能范围

1. **页面停摆自愈**：取数过程中探测到页面不干活（请求挂起超时、opencli 调用失败）时，自动重建标签页并重试该请求；恢复后继续下载，不打断用户正常用电脑。
2. **无法自愈时如实暂停**：Edge 被关闭、扩展断连、登录失效等恢复不了的情况，停止并给出具体原因与操作指引，保留已完成进度，不硬撑不空转。
3. **报错带出底层原因**：任何取数失败的记录（告警、任务状态、取数说明）都必须包含底层具体原因，不再只剩"网络错误达到重试上限"这类外壳；同时遵守既有约束：不输出账号登录内容。
4. **逐家落盘断点续跑**（方案已确认）：每成功取完一家立即落盘保存进度；重跑时自动跳过已保存的公司，从断点继续。中途任何意外不再丢失整轮进度。
5. **失败公司如实留痕**：逐家取数尝试过但失败的公司，必须写进取数说明的取数范围与失败原因，报告里如实呈现为"取数失败/未取得"，不得显示为"取数范围外、属正常情况"。（此项为本需求相对情况说明的补充，依据是本技能"不得把残缺数据写成无数据结论"的既有原则；如不同意可去掉。）
6. **同步更新 README**（含调试记录），完成本地验证后提交并推送 GitHub（用户已明确授权）。
