# 下载可靠性修复设计方案

日期：2026-10-25
状态：推荐方案一（检查点 2 按用户"后续步骤请全程自主执行"指令连续通过）
需求依据：`docs/requirements/2026-10-25-下载可靠性修复需求.md`

## 问题定位（设计输入）

三条已证实的故障链：

1. **页面停摆**：取数标签页进入后台冻结态（`document.visibilityState = hidden`）后，页面内异步任务（定时器、fetch 回调）被挂起——同步求值仍秒回，但任何"等一等再继续"的调用永不完成。实测 300 毫秒定时器 12 秒不触发、`fetch` 永不返回；重建标签页后立即恢复。
2. **报错吞真因**：上述底层错误（调用超时 / opencli 返回码非 0（如 cdp_timeout）/ 扩展断连）统一被客户端翻成"网络错误达到重试上限"，只留外壳。历史现场"约 14—17 秒失败一次"与"opencli 快速失败 + 限速等待 + 两次退避"的耗时吻合，说明当时是快速失败路径，同样被外壳吞掉。
3. **全存后写**：`collect_by_company` 把所有企业资料攒在内存，全部抓完才写盘；一次失败废掉整轮。且 `取数说明.json` 的取数范围只记成功公司，失败公司在报告里被误标为"取数范围外、属正常情况"。

## 方案比较

### 方案一：传输层自愈 + 逐家进度文件（推荐）

在 `OpenCliTransport` 内建"页面体检—重建标签页—重试"闭环；逐家取数每成功一家立即写进度文件，重跑跳过已完成；失败公司带原因写进取数说明并在报告标"取数失败"；不可恢复时快速中止并暂停。

- 优点：直接消除 2.5 小时空转（历史故障下首家公司几秒内中止，而非耗完整轮）；对批量导出路径同样生效（同一传输层）；改动集中在既有模块，无新依赖、无并行进程。
- 缺点：触及传输层（根因已测准，满足"先测准再改"前提）；需要区分"可自愈/不可自愈"两类错误。
- 实现成本：中。风险：自愈动作会新建取数标签页（本技能本就会开页面，属既有行为）。

### 方案二：外部看门狗进程 + 最小代码改动

另起一个监控脚本发现卡死就重启任务，技能代码只加逐家落盘。

- 优点：不动传输层。
- 缺点：双进程并发正是 Bug 2（状态文件互踩）的教训来源；看门狗与技能状态难以一致；用户要额外管一个进程。**否决。**

### 方案三：客户端层拉长退避重试

保留现状，只加大重试次数与等待，指望页面自己醒过来。

- 优点：改动最小。
- 缺点：后台冻结的页面不会自愈，重试只会把 2.5 小时空转变成更长空转；真因照旧被吞。**否决。**

### 方案一内部的落盘形态选择

- 单个 `逐家进度.json`（每成功一家原子重写）：与既有 `state_io.atomic_write_json` 一致，读写简单，108 家规模下文件仅几百 KB。**选用。**
- 每家一个 JSON 文件：抗崩溃略强但目录杂乱，且最终仍要聚合。
- 追加写 xlsx：openpyxl 无安全追加语义，崩溃即损坏。否决。

## 推荐方案设计（方案一）

### 1. 传输层自愈（scripts/cicpa/browser_transport.py）

- 新增 `ChannelDeadError(OpenCliBridgeError)`：不可恢复的通道死亡（opencli 缺失、扩展断连、Edge 被关闭、重建后重试仍失败），消息含底层原因与操作指引。
- `_eval` 内的失败（子进程超时、返回码非 0、envelope 解析失败）触发自愈：
  1. `tab new <注协首页>` 重建取数标签页（实测冻结态下该命令仍可用）；
  2. 重试原调用，取到数就算好——**不以可见性论生死**（2026-10-25 复测更正：窗口最小化后新建标签页 0.3 秒正常返回，最小化后台跑是合法用法）；
  3. 仍失败则抛错并带上前后两次的底层原因。
- 自愈失败分类：opencli/扩展不可用 → `ChannelDeadError("请确认 Edge 已打开且 OpenCLI 扩展已启用…")`；重试仍失败 → 错误含前后原因。
- `verify_session` 纳入同一自愈：不再因调用超时抛裸 OSError。
- `request()` 的域名守卫与 nav 重试逻辑不动。

### 2. 报错带出真因（scripts/cicpa/client.py）

- `TemporaryApiError("网络错误达到重试上限")` 消息追加底层异常文本（含 cause 链摘要），如"网络错误达到重试上限：opencli 调用超时"。
- `ChannelDeadError` 属 RuntimeError，天然穿透客户端重试循环（立即上抛、不退避空转）。

### 3. 逐家落盘与断点续跑（scripts/逐家取数.py）

- `collect_by_company` 改为：
  - 进度文件 `逐家进度.json`（位于补采目录）：`{"completed": {公司名: 资料}, "failed": {公司名: 原因}, "updated_at": …}`，每成功/失败一家立即原子写入；
  - 开跑先加载进度，**跳过 completed 公司**，failed 公司重试；
  - 最终 `write_dimension_files` 用「进度中已有 + 本次新取」的全量资料生成五个维度文件；
  - `取数说明.json` 的 `company_names` 改为**全部尝试过的公司**，新增 `failed_companies`（公司名 → 带真因的失败原因）；
  - 循环内 `ChannelDeadError` 直接上抛中止（不再逐家耗完），其余异常仍按单家失败记录后继续；
  - 全部失败时抛出的错误信息带上失败原因摘要。
- 重跑语义：同一补采目录、同一公司名单续跑，自动跳过已完成、重试失败项。

### 4. 报告如实标注（scripts/related_party_check.py + scripts/报告输出.py）

- `build_dim_index` 读取 `failed_companies`，随 `file_info` 传递。
- `coverage_rows`：公司无记录但有失败原因时状态为**"取数失败"**（明细列写原因），不再落入"取数范围外、属正常情况"；有记录时仍以"已取得记录"为准。
- 缺口页：同维度 ≥2 家"取数失败"折叠为一行汇总（原因取并集，注明逐家明细见 `取数说明.json`），避免百行重复；公司名单页仍逐家列示。"取数失败"计入资料缺口与重度缺口统计。
- 相关状态不进 `ok_status`。

### 5. 编排层暂停（scripts/related_party_workflow.py）

- 候选企业补采阶段：`ChannelDeadError` 或"全部失败"的 `SingleCompanyError` 改走 `_pause_export` 暂停（保留进度、如实报原因），不再"告警后继续出 0 结论报告"。部分成功仍继续出报告（缺口如实标注）。
- 主体保底路径本就暂停，不改。

### 6. 术语与决策记录

- `CONTEXT.md`：新增"取数失败（公司级）"术语（区别于"取数范围外"）；"逐家取数（保底通道）"补断点续跑语义。
- `docs/adr/0002-页面停摆自愈采用重建标签页.md`：记录"自动重建取数标签页、而非要求用户保持 Edge 前台"的取舍（用户明确选择 A）。

## 数据流（修复后）

```
collect_by_company
  ├─ 读 逐家进度.json → completed 跳过
  ├─ 逐家 fetch_company
  │    └─ client.request_json → OpenCliTransport.request
  │         └─ _eval 失败？→ 重建标签页 → 重试原请求一次（以实际取到数为准）
  │              ├─ 成功 → 返回
  │              └─ 不可恢复 → ChannelDeadError（带真因+指引）→ 中止循环
  ├─ 每家结束 → 原子写 逐家进度.json
  └─ 全部完成 → write_dimension_files（全量）+ write_scope_note（含 failed_companies）
```

## 错误处理

| 场景 | 行为 |
|---|---|
| 标签页后台冻结 / 被对话框挡住 / 被导航走 | 自动重建标签页并重试，任务继续 |
| Edge 最小化 / 在后台跑 | 正常工作（2026-10-25 复测更正：不受影响） |
| Edge 关闭 / 扩展断连 | `ChannelDeadError` 暂停，提示打开 Edge 并启用扩展，进度保留 |
| 登录失效 | 沿用既有登录引导（`wait_for_login`），不代登录 |
| 单家企业业务失败（名称无法匹配等） | 记入 `failed_companies`，继续下一家 |
| 重跑续跑 | 跳过 completed、重试 failed，不重取已完成公司 |

## 测试策略

1. `test_client.py`：底层异常文本出现在 `TemporaryApiError` 消息中。
2. `test_browser_transport.py`（假 runner）：调用失败→重建→重试成功；重建后隐藏但取数成功仍视为正常；重试仍失败 → `ChannelDeadError` 且错误含前后原因与续跑指引；扩展断连 → 指引型 `ChannelDeadError`。
3. `test_逐家取数.py`：中途崩溃后重跑跳过已完成、重试失败项；`取数说明.json` 含全部尝试公司与 `failed_companies`；`ChannelDeadError` 立即中止；进度文件逐家落盘（第二次调用前可见首次成果）。
4. 报告测试：失败公司标"取数失败"而非"取数范围外"；折叠汇总正确；缺口统计含失败公司。
5. 编排测试：候选补采通道死亡 → `paused_export` 且进度保留。
6. 全量回归 + `validate_bundle.py`；真实冒烟 1 家走通取数链路（需 Edge 会话）。

## 迁移与回滚

- 进度文件与 `failed_companies` 均为新增字段，旧目录无这两个字段时按现状处理（无进度即全新开始、无失败标注即旧行为），向后兼容。
- 回滚：单提交还原即可；进度文件不影响旧版运行（旧版忽略它）。
