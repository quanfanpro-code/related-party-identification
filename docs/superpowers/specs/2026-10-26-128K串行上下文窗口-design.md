# related-party-identification：128K 串行上下文窗口设计

日期：2026-10-26  
状态：按用户“自主推进后续流程、实际编码前停止”的授权定稿  
需求依据：`docs/requirements/2026-10-26-128K串行上下文窗口-requirement.md`

## 1. 设计目标与硬边界

新增只负责上下文调度的外壳。1M 保持现有流程；128K 使用同一模型的串行独立窗口。20 维取数、候选扩张、穿透与确认点、证据比对、缺口、来源追溯和八表报告均不缩减。

本设计不修改 `related_party_workflow.py`、`related_party_check.py`、发现引擎、导出器或报告输出程序。

## 2. 方案比较

| 方案 | 成本与维护 | 等价性、风险与验证 | 可逆性 | 结论 |
|---|---|---|---|---|
| A：原技能内分流＋状态摘要＋串行独立窗口 | 新增说明和只读调度工具，复用现有状态与报告引擎 | 可用同一离线导出目录比较完整报告；需验证大范围确认和窗口交接 | 停用新增入口即可恢复 | 推荐 |
| B：复制 128K 精简技能 | 两套取数、规则和报告说明需同步 | 容易减少维度、候选或证据，规则漂移风险高 | 可回退但维护成本高 | 否决 |
| C：只压缩说明和输出，不隔离窗口 | 改动较少 | 长对话中的候选和报告历史仍累积 | 易回退 | 不满足硬门槛 |
| D：外部模型 API 或并行抓取 | 需新配置与调用链 | 改变模型、数据路径、并发和注协访问节奏 | 回退成本高 | 否决 |

## 3. 推荐架构

### 3.1 原技能内双入口

在 `SKILL.md` 前置元数据后增加一次询问：“本次使用 1M 还是 128K 上下文模型”。

- 1M：执行现有正文，不创建调度文件。
- 128K：读取 `references/128K串行上下文.md`，沿用原 `related_party_workflow.py` 和原业务状态。
- 新任务只问一次，续作窗口继承选择；没有活动任务且用户明确要求时才变更模式，业务状态不重置。
- 不新建同名技能或另一套触发说明。

### 3.2 三层职责

1. **业务核心**：现有任务状态、导出状态、候选记录、原始文件、核查规则和报告，仍是唯一业务真相。
2. **主控窗口**：负责用户沟通、简要状态、范围确认和逐个调度，不反复读取完整候选记录、20 维原始表或整份报告。
3. **执行窗口**：只在原流程确实需要 Agent 阅读、解释或复核时启动，一次处理一个完整逻辑任务，读取完整必需资料并保存结果，只返回短回执。

取数本来由程序串行完成，不为了“使用新窗口”额外增加 Agent 调用。所有独立窗口均前台串行，禁止后台或并行执行。

## 4. 各入口的任务边界

### 4.1 主动发现

- 原 20 维取数、默认五层、持股阈值、候选上限、补采和缺口流程不变。
- 主控通过调度工具读取 `stage/status/message_zh/candidate_count/report_paths` 等简要字段，不整体打印含 `candidate_records` 的任务状态。
- 到达候选或深度确认点时，完整候选记录仍保存在 `候选发现记录.json` 和原状态中；用户确认的范围不得缩小。
- 候选及来源需要分页展示时，调度工具按稳定顺序输出一页；所有页面合计必须等于原完整集合，不重复、不遗漏。分页只改变展示，不改变确认对象或后续取数名单。
- 用户确认后仍调用原 `resume`，不能只处理已展示页面。

### 4.2 名单核查

- 名称列歧义、候选上限和用户确认流程不变。
- 主控只读取列名、数量和具体歧义，不为了节省上下文把整个名单反复贴入对话。
- 实际查询仍覆盖原名单全部公司。

### 4.3 已有数据离线核查

- 仍不登录、不联网，直接调用原核查程序。
- 原始 Excel 由程序完整读取；模型只处理原流程要求的异常、缺口和报告解释，不逐文件朗读原始数据。
- 需要逐公司解释时，一个执行窗口处理一个完整公司对或一个完整报告任务，不能漏掉高、中风险或缺口。

## 5. 调度状态与短回执

### 5.1 辅助文件

在原 `--state-path` 所在目录新增：

- `上下文调度状态.json`：模式、模型绑定、当前占用、主控调度计数、原状态路径及 SHA-256。
- `上下文调度记录.jsonl`：开始、完成、恢复和轮换记录，仅供程序核查。

原任务状态、导出状态、候选发现记录和报告仍是唯一业务依据。辅助文件不能证明某维度、候选或报告已经完成。

### 5.2 调度工具

新增 `scripts/串行上下文调度.py`，只使用 Python 标准库：

- `初始化`：仅在 128K 模式创建辅助状态。
- `开始`：登记一个完整逻辑任务及输入锚点；有活动占用则拒绝。
- `完成`：在原工作流或报告程序接受并保存结果后登记哈希并解除占用。
- `状态`：输出简要任务状态和路径，不输出完整候选记录。
- `候选页`：仅在范围确认需要时按页读取完整候选集合，返回页码、总数和本页原文；不改变集合。
- `交接`：形成新主控窗口所需的简短续作信息。
- `恢复`：显式记录异常恢复并解除陈旧占用，下一步仍从原任务状态判断。

执行窗口只返回任务编号、`saved / needs_retry / blocked`、结果路径、哈希和一句技术状态，不返回整份候选、证据或报告正文。

主控窗口默认最多完成 20 次调度后轮换，宿主提前预警时立即轮换。该限制只控制对话历史，不改变维度批次或候选批次。

## 6. 数据流

```text
用户选择 1M
  └─ 原 SKILL → 原工作流与报告，不创建辅助文件

用户选择 128K
  └─ 原 preflight / run / resume → 简要状态
       → 无需 Agent 的步骤继续由原程序串行完成
       → 需要独立阅读时登记一个任务 → 前台启动一个执行窗口
       → 完整读取所需资料 → 保存原格式结果 → 短回执
       → 原程序校验或保存 → 解除占用 → 下一任务或主控轮换
```

## 7. 宿主适配与失败处理

| 场景 | 处理 |
|---|---|
| 宿主支持当前模型的独立 Agent | 前台串行调用，不指定其他模型 |
| 不能保证同一模型或窗口隔离 | 改用同模型手工独立对话；无法保证时停止 128K 路径 |
| 候选确认内容过大 | 分页展示完整集合；不得只确认已显示的一部分 |
| 单个完整逻辑任务无法装入 | 停止并报告，不减少公司、维度或证据 |
| 原状态或输入哈希变化 | 停止续跑，查明版本，不覆盖旧证据 |
| 活动占用未解除 | 禁止下一任务，显式恢复后继续 |
| 取数或核查失败 | 完全沿用原 missing、降级、暂停和缺口规则 |
| 用户选择 1M | 不创建、不读取、不依赖辅助文件 |

## 8. 等价测试策略

1. **基线**：先运行现有全量测试和 `scripts/validate_bundle.py`，记录数量及既有问题。
2. **路由与串行**：1M 不创建辅助文件；128K 活动占用拒绝第二个任务；恢复不伪造完成。
3. **状态摘要**：简要输出不包含完整 `candidate_records`，但原状态文件内容和哈希不因读取改变。
4. **候选分页**：多页合并后的公司、来源和路径与原集合逐项一致；确认后原 `resume` 收到完整名单。
5. **离线确定性等价**：同一导出目录分别走原核查命令和 128K 调度，比较候选、命中、风险、缺口、证据来源、链接以及八表报告的单元格值、公式和结构。
6. **断点**：在取数中、候选待确认、报告前、结果保存后未解除占用和主控轮换处恢复，不重复下载、不漏候选、不扩大范围。
7. **实际 128K 验收**：同一模型串行处理代表性候选规模，核对高风险证据、可疑红旗、缺口和报告解读不下降。
8. **回归**：运行既有全部测试、分发包校验和 Excel 验收；真实在线取数不作为普通单元测试前提。

## 9. 迁移与回滚

- 不迁移或改写旧任务状态、导出状态和原始证据。
- 辅助状态锚定原任务状态；不一致时停止，不强行接续。
- 回滚时停用新增入口和辅助脚本，原工作流、旧状态和报告不受影响；不删除任何资料。
- 默认不执行 Git 提交、推送或分支清理。

## 11. 设计自审与检查点 2

- 没有把减少维度、候选或报告内容当作上下文优化。
- 简要状态只用于调度，候选分页覆盖完整集合，不能改变用户确认范围。
- 原程序和原状态仍是唯一业务真相，辅助文件不能代替完成证据。
- 单任务装不下或宿主不能隔离时明确停止，不静默降级。
- 按用户自主推进授权，采用方案 A 连续进入实施计划编写；本轮不产生业务代码。
